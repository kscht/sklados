# Канонизация статусов — `vocab:domovoy_status` (D-32)

Предложение по [D-32](decisions.md): дедупликация всех значений `status` из корпуса и модель словаря. Парный документ к [`kind-audit-domains.md`](kind-audit-domains.md) — носители state machine взяты оттуда.

## Инвентарь

Полный grep `database.md` (кавычная нотация + псевдо-нотация + enum-перечни в тексте): **~60 сырых значений**. Основные группы дублей:

| Дубли | Причина |
|---|---|
| `ожидание` / `ожидает` / `ожидается` | три написания, **три разных смысла** (очередь / блокировка / обещание) |
| `выполнено` / `выполнена` / `выполняется` / `завершён` / `готов` / `готова` / `completed` | род/вид/язык |
| `активен` / `активна` / `активно` / `active` | род/язык |
| `в процессе` / `в-процессе` / `running` / `запущен` | написание/язык |
| `ошибка` / `ошибка-генерации` / `failed` | язык/специализация |
| `черновик` / `идея` / `draft` | синонимы |
| `актуален` / `актуально` / `устарел` / `устарело` / `deprecated` | род/язык |

## Модель: scoped под-схемы в одном словаре

Плоский enum невозможен — он противоречит критерию №2 выделения `kind` (разные state machines ⇒ разные наборы статусов). Модель:

```
vocab:domovoy_status                     (kind='vocabulary')
├── status_set_task                      (kind='concept', под-схема)
│   ├── concept: not_started             (part_of → status_set_task)
│   ├── concept: in_progress
│   └── ...
├── status_set_job
│   ├── concept: queued
│   └── ...
└── ...
```

- **Концепт статуса** несёт `identifier` (slug), `_i18n` (ru/en метки), `color` (для `StatusChip` и `auto:status` из [`ui-architecture.md`](ui-architecture.md)), опц. `order` (позиция в жизненном цикле).
- Общие статусы (`done`, `cancelled`, `failed`…) — **один концепт с несколькими `part_of`** в разные под-схемы (та же норма, что в categorization.md для категорий).
- Валидация «задаче нельзя поставить `оплачен`» — тем же механизмом, что каталог рёбер: `fn::check_status($kind, $status)` читает под-схему.
- На узле — только slug: `status='in_progress'`. Переводы и цвета живут в концепте, **не в коде UI** (поправка к раздел i18n в database.md).

## Под-схемы по носителям SM (16)

| Под-схема | Slug-и (порядок = жизненный цикл) | Мигрирует из |
|---|---|---|
| `task` | `not_started → in_progress → done`; `waiting`, `paused`, `cancelled` | не начато, в процессе, выполнено/-а, ожидает, на паузе, отменено |
| `job` | `queued → running → done`; `failed`, `cancelled`, `skipped` | **ожидание**, запущен/выполняется, завершён, ошибка/-генерации, отменён, skipped/completed/running |
| `worker` | `active → draining → dead` | активен, завершает, мёртв (свободен/занят — **не статус**, выводится из `current_job`) |
| `order` | `new → confirmed → paid → picking → ready → shipped → delivered → done`; `cancelled` | новый, подтверждён, оплачен, собирается, готов, отправлен, доставлен, выполнен, отменён |
| `order_return` | `requested → approved → received → refunded`; `rejected` | запрошен, одобрен, получен, завершён, отклонён |
| `payment` | `pending → paid`; `failed`, `refunded` | ожидает, оплачен, ошибка, возврат |
| `delivery` | `new → in_transit → customs → delivered`; `undelivered`, `returned` | оформлен, в пути, на таможне, получено, не доставлено, возврат |
| `listing` | `active`; `sold_out`, `withdrawn` | активно, распродано, снято |
| `incident` | `reported → triage → mitigating → resolved → post_mortem` | открыт, … (набор из kind-audit) |
| `appeal` | `filed → review → decided`; `appealed` | подано, рассмотрение, решено, обжаловано |
| `attempt` | `in_progress → passed / failed`; `abandoned` | активна, завершена, прервана |
| `rule_breaker` | `closed → open → half_open` | закрыт, открыт, полуоткрыт |
| `content` | `draft → in_review → approved → published → archived` | черновик/идея, на_согласовании, согласовано/проверен, опубликован, архив |
| `event` | `planned → active → done`; `cancelled` | запланирован, активно, завершён |
| `notification` | `queued → sent`; `failed`, `read` | ожидает, отправлено, ошибка, прочитано |
| `promise` | `pending → kept / broken` | ожидается, выполнено, нарушено |

**Итого: ~45 уникальных slug-концептов** (общие переиспользуются между под-схемами) — не «~10», как оценивал `kind-audit.md`, и не 60, как в сыром корпусе.

## Не-статусы (вычищаются из поля `status`)

| Значение | Что это на самом деле | Куда |
|---|---|---|
| `ai` | тип автора сообщения | поле `author_type` |
| `удалён` | soft delete | механизм корзины (`_deleted`/`deleted_at`), не статус |
| `актуален` / `устарел` / `deprecated` | позиция в цепочке версий | **вычислимо** из `supersedes` (голова цепочки = актуален); не хранить |
| `актуально` / `нужно-обновить` | свежесть перевода | метаданные `_i18n` (stale detection), не статус узла |
| `нужен` | желание купить | ребро `needs` / вишлист, не статус |
| `свободен` / `занят` (воркер) | наличие текущего job | вычислимо из `current_job` |

## Контракт воркеров

Захват задачи (`CLAUDE.md`, database.md:8319) меняется на slug:

```surql
UPDATE thing SET status = 'running', locked_by = $worker_id, ...
WHERE id = $job_id AND status = 'queued' AND locked_by = NONE;
```

`status = "ожидание"` → `status = 'queued'`. Правка `CLAUDE.md` — после утверждения D-32 (кода, зависящего от старого значения, ещё нет — сейчас самый дешёвый момент).

## Что меняется в фазе 1

1. В seed добавляется блок `vocab:domovoy_status`: 16 под-схем + ~45 концептов с `_i18n` ru/en и `color`.
2. Все `status` в seed мигрируются по таблицам выше **тем же коммитом, что `kind`** (иначе seed переписывается дважды).
3. Для инвентарной вертикали реально нужны только `task`-набор (фаза 9, lent-workflow косвенно) — остальные под-схемы заливаются как словарь без узлов-носителей.
4. `fn::check_status` — вместе с `fn::check_edge` при реализации валидации (не блокирует фазу 1).

## Резюме

> Сырых значений статусов — ~60, канонических — **~45 slug-ов в 16 scoped под-схемах**; шесть групп значений (`ai`, `удалён`, версии, свежесть перевода, `нужен`, `свободен/занят`) — вообще не статусы и выносятся из поля. Три написания «ожидания» разводятся по смыслу: `queued` (очередь) / `waiting` (блокировка) / `pending` (обещание/платёж). Контракт воркеров переводится на `queued` до появления первого кода.
