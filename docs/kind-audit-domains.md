# Аудит `kind` по доменам database.md — расширение канона 27 → ~40

Закрывает [D-31 и D-36](decisions.md). Первый аудит ([`kind-audit.md`](kind-audit.md)) прогнал строгий тест по **seed** (56 значений → 27 канонических). Этот документ прогоняет тот же тест по **`database.md`** — доменам, которых в seed ещё нет.

Строгий тест (из `kind-audit.md`): отдельный `kind` заслуживает сущность, у которой есть хотя бы одно из: **(1)** эксклюзивное ребро / ребро меняет семантику; **(2)** собственный state machine; **(3)** отдельный способ существования. Недостаточно: свой UI-экран, много полей, развитый workflow, «концептуально другое».

## Поправка к docs-audit

Полный инвентарь `database.md` (кавычная нотация + псевдо-нотация `kind: X` + заголовки `### kind:`) даёт **118 уникальных значений**, а не ~77, как указано в [`docs-audit.md`](docs-audit.md). Недооценка первого аудита — не ×7, а **×10** (заявлено 9 «упоминаемых только в database.md», реально ~100 вне канона).

## Итог сразу

> **27 существующих + 14 новых = 41 канонический `kind`**. Прогноз docs-audit (35–45) подтверждён. Остальные ~90 значений складываются в существующие `kind` через `subtype`/`category`/поля/рёбра.
>
> **Утверждено 2026-07-21** (D-31, D-37): канон = 41, включая `step`.

## Спорные случаи — на решение

| # | Случай | Варианты | Склоняюсь к |
|---|---|---|---|
| 1 | `step` — kind или `template(subtype)` | см. выше | отдельный `kind` (оркестратору ходить по DAG) |
| 2 | `контакт-метод` — узлы (гранулярный шаринг через `can_access`) или embedded на `person` | узлы дают приватность per-метод; embedded проще | embedded + field-PERMISSIONS; вернуться при потребности |
| 3 | `отправка` — `task(subtype delivery)` или свой `kind` (SM трекинга) | сценарий «сложный трекинг» в database.md не перечитан детально | `task` |
| 4 | `курс`/`квиз` — `template` или `page` | двойная природа: контент + порождение прохождений | `template` |
| 5 | Канонический `kind` для абстрактных контейнеров (коллекция промптов, корневые контейнеры системы) | `group(subtype collection)` vs собственный `collection` | расширить `group` |
| 6 | `дневник`/`блог`/`сайт` как `page`-контейнеры — не перегружаем ли `page` | — | принять; пересмотреть при реализации домена |

## Мета-классы субъектов (дополнение по D-43)

`vocab:domovoy_kind` дополнительно содержит **классы-группировки** (`is_class=true`, не значения `kind`): `party` = person/group/org («взято у другой семьи» = `borrowed_from → group`), `actor` = party + agent/worker/gateway (исполнители). Используются в `from_kinds`/`to_kinds` каталога рёбер с разворачиванием по `part_of` — см. [`relation-typing.md`](relation-typing.md).

## Что это меняет в фазе 1

1. `vocab:domovoy_kind` заливается с **41** концептом (не 27); `_i18n` ru/en на каждый.
2. Для инвентаря ничего не меняется: его `kind` (`item`, `location`, `person`) не тронуты.
3. Автоматизационные `kind` (`job`, `rule`, `worker`, …) в seed фазы 1 — **только концепты словаря**, без узлов-экземпляров: узлы появятся при реализации воркеров.
4. Статусная миграция (D-32) получает точный список носителей SM: `task`, `appeal`, `payment`, `event`, `incident`, `listing`, `order`, `job`, `worker`, `attempt`, `rule` — по под-схеме статусов на каждый.

## Резюме

> Полный инвентарь `database.md` — **118** уникальных `kind`. Строгий тест пропускает **13 новых** канонических (`job`, `rule`, `datasource`, `gateway`, `worker`, `chat`, `agent`, `service`, `order`, `view`, `block`, `question`, `attempt`), один спорный (`step`), остальные ~90 складываются в существующие через subtype/category/поля/рёбра — включая два случая, где узлы правильнее превратить в **рёбра** (позиции заказа → `requires`/`used`, карточки повторения → ребро с SM-2 полями). Канон: **27 → ~40**. Стрей-рёбра закрыты заменами на существующие; каталог рёбер остаётся 27.
